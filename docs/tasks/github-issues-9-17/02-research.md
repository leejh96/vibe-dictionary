## 검색과 추천 키워드

평가 데이터는 실제 로그가 아닌, 측정 전에 고정한 합성 사용자 표현이다. `packages/catalog/tests/search-evaluation.ts`에서 기대 ID와 허용 대안을 관리한다. “반투명 유리 카드”에는 액체 아크릴 스타일도 허용 대안으로 정의했다. 표시 언어는 검색 언어와 분리한다.

| 같은 20개 긍정 문장 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| Top-1 적중률 | 80% | 90% |
| Top-3 적중률 | 85% | 100% |
| 검색 결과 없음 | 5% | 0% |

무관한 3문장은 전후 모두 결과가 없었다. 확인한 실패는 `flips`, `scrolling continuously`, `얼굴만 흐리게 가리는`였다. 활용형·스크롤·지속·얼굴·흐림의 동의어를 추가했으며 필드 가중치나 60% 토큰 커버리지 기준은 변경하지 않았다. 이 표현들은 실제 MCP stdio 연결에서도 검증했다.

추천 키워드는 카탈로그 순서를 유지하고 각 기법의 첫 키워드를 사용한다. 같은 도메인에서 한영 각각 중복이 없고 모든 키워드가 해당 기법을 같은 카테고리의 결과에 포함했다. 유사 의미의 다른 키워드를 임의로 병합하거나 추천 순서를 바꾸지 않았다. 선택 칩이 접힌 10개 안에 남고, 같은 칩을 다시 누르면 검색이 해제되는 동작을 회귀 테스트로 유지한다.

재실행 명령:

```sh
npm run evaluate:search
npm run audit:keywords
npm run test:catalog
npm run test:mcp
```

## 브라우저·성능 검증 범위

Windows에서 연결한 Chrome과 로컬 Vite·프로덕션 미리보기를 사용했다. iframe 계측은 UI 입력의 대상이 의도대로 유지되는지 확실하지 않아 필터·스크롤 비교의 근거에서 제외했다. 이후 실제 앱 문서에 로컬 전용 계측을 붙여 직접 입력했다. 계측 스크립트·스크린샷·원시 JSON은 제품·배포 원본에 포함하지 않았다.

DOM·마운트 수, 브라우저 힙 관측과 Long Task는 진단용 기준선이다. 프레임 간격은 전면·백그라운드 전환 및 도구 자체 부하의 영향을 받고 1초 이상 간격을 제외했으므로 FPS 보장으로 사용하지 않는다. 힙은 GC를 통제하지 않았으므로 누수 없음의 증거가 아니다. 특정 탭의 격리된 CPU 사용률·강제 GC·모바일 네트워크/CPU 제한을 제공하는 도구는 이번 검증 환경에 없었다. CPU 모델 조회도 제한되어 기기별 성능 수치를 일반화하지 않는다.

실제 앱에서 확인한 동작은 다음과 같다.

- 돌리 줌의 조절 슬라이더가 화면·접근성 트리에 나타나지 않고, SVG 배경은 시간에 따라 변한다. 클릭하면 초기 원근에서 다시 진행한다.
- 추가 재생 버튼의 키보드 초기화는 당시 확인했으나, 이후 사용자 요청에 따라 버튼 자체를 제거했다. 390px 뷰포트의 카드 배치와 가로 넘침을 확인하고, 라이트·다크 테마를 확인했다. 뷰포트 검사는 실제 모바일 터치 검증과 구분한다.
- 조합기를 열면 적용 대상에 포커스가 오고 Tab·Shift+Tab이 양 끝에서 순환한다. Escape로 닫으면 원래 조합기 버튼에 포커스가 복귀한다.
- 한국어·영어의 5개 도메인 라벨, 실제 클립보드 원문, 라이트·다크, 새로고침 후 선택·적용 대상 복원을 확인했다.
- 새 미리보기의 화면 밖·숨긴 문서·모션 감소·언마운트 타이머 해제, 클릭 초기화와 공통 호버 이벤트 부재는 자동 회귀로 확인한다. 리플·에러 셰이크의 지연 작업도 언마운트 시 해제되는지 검사한다.

OS 모션 감소 설정이 활성화된 실제 브라우저, 스크린리더, 다른 브라우저와 물리적인 모바일 터치는 확인하지 않았다. 브라우저 도구가 모션 선호도 에뮬레이션을 노출하지 않아 이 항목은 자동 모의 검증과 구분한다. 실기기·장시간 성능 및 이 접근성 항목이 남아 있으므로 전체 이슈의 실환경 검증 완료로 표현하지 않는다.

초기 자동 검증은 `npm test`에서 카탈로그 6개·웹 372개·MCP 9개, 합계 387개가 통과했다. `npm run build`, `npm run lint`, `git diff --check`도 통과했다. 번역 검사는 1,394개 한영 키를 확인했다. 당시 프로덕션 JS는 2,618.86kB / gzip 762.86kB였고 기존 큰 청크 경고는 남아 있었다.

### 자동 재생 끊김 후속 수정

사용자가 지적한 부드럽지 않은 재생은 새 시연 시계의 `setInterval(80)`와 범위값 반올림에서 확인했다. 8초 반복 주기 자체와 별개로 초당 12.5회만 값을 바꾸므로 연속 효과도 계단식으로 보였다. `requestAnimationFrame` 경과 시간과 연속값 보간으로 바꾸고, 파생 상태를 효과에서 다시 저장하던 추가 렌더도 제거했다. 탭 인덱스·포스터 색상 단계·돌출 층수의 정수 계약은 명시적인 `steps` 모드로 유지했다. 반주기 트리거는 별도 컨텍스트로 분리했다.

같은 Chrome의 1,849px 콘텐츠 폭에서 돌리 줌의 첫 배경 프레임 `width`가 바뀌는 간격을 관측했다. 각 4초의 짧은 로컬 표본이며 디스플레이·도구·시스템 부하가 통제된 성능 보장은 아니다.

| 돌리 줌 SVG 변화 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 관측 갱신 횟수 | 49 | 575 |
| 갱신 간격 중앙값 | 83.3ms | 6.9ms |
| 갱신 간격 95백분위 | 104.1ms | 7.0ms |

화면 주사율에 맞춰 갱신하되 반복 속도는 동일하다. 16ms·8ms 간격의 모의 프레임에서 동일 경과 시간의 값이 같은지, 80ms보다 짧은 시점에 소수점으로 이동하는지, 일시 중단 시간이 복귀 시 진행률을 건너뛰게 하지 않는지 추가 검사했다. 전체 검증은 카탈로그 6개·웹 374개·MCP 9개, 합계 389개와 빌드·ESLint·diff 검사 통과다. 모든 데모의 실기기 FPS나 제미나이 생성물과의 직접 비교를 수행한 것은 아니다.

### 클릭 전용 재시작 후속 수정

마지막 상호작용 수정에서 공통 `DemoAutoplay`·`useDemoReplay`의 포인터 진입 재시작과 카드의 추가 재생 버튼·상태·번역 키를 제거했다. 타이핑·스크램블·형광펜에 따로 있던 호버 재시작도 제거했고, 스크램블의 한영 프롬프트를 클릭 동작에 맞췄다. 버튼 채움·레이어 펼침·포인터 추적은 해당 디자인의 상호작용으로 유지한다. 이 입력을 처리하는 동안 자동 시연값이 실제 입력값을 덮어쓰지 않으며, 포인터를 빼면 기존 시연 시계의 현재 위치로 돌아간다. 호버로 공통 시계를 초기화하지 않는다.

브라우저에서 추가 재생 버튼이 0개이고 데모 클릭 시 미리보기 인스턴스가 바뀌는 것을 확인했다. 공통 호버 이벤트 부재, 갤러리 안에서 버튼 채움·포인터 추적 입력 처리와 시연 복귀는 회귀 테스트로 확인했다. 실제 마우스 호버는 이번 브라우저 도구로 재현하지 않았다. 최종 카탈로그 6개·웹 376개·MCP 9개, 합계 391개 테스트와 전체 빌드·ESLint·diff 검사가 통과했다.

### 내부 클릭 동작 보존 후속 수정

원근·정투영 버튼과 아이리스 클릭 영역에서 공통 재시작이 기존 핸들러를 가로막는 문제를 회귀 테스트로 재현했다. 이벤트 통과만 수정한 뒤에도 자동 시연값이 수동 상태를 덮어쓰는 별도 실패를 확인했다. 내부 버튼·입력 및 기존 사용자 지정 클릭 영역을 공통 재시작에서 제외하고, 숫자·토글 setter가 현재 표시값을 기준으로 변경을 적용하도록 수정했다. 기존 `div`·`span`·`li` 클릭 영역 69곳은 `data-demo-control`로 표시하고 두 공통 재생 훅에서 같은 제외 기준을 사용한다. 새 클릭 영역도 이 계약을 따르는지 정적 회귀로 확인한다.

OTP는 임의의 자동 샘플값으로 입력을 덮어쓰지 않고, 기존 순서 재생 핸들러를 자동 시연과 버튼이 함께 사용한다. 단계 이동·OTP의 시간별 결과도 회귀 테스트로 확인했다. 브라우저에서는 정투영→원근 양방향 선택과 동일 SVG ID 유지, 아이리스 마스크의 0%↔120% 전환을 직접 확인했다. 자동 재생·공통 호버 재시작 부재·추가 재생 버튼 제거는 유지했다. 최종 검증은 카탈로그 6개·웹 381개·MCP 9개, 합계 396개 테스트와 전체 빌드·ESLint·diff 검사 통과다. 기존 실기기 성능·OS 접근성 검증 한계는 별도로 남아 있다.
